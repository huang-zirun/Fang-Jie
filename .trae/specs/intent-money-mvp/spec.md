# 意图选择式赚钱系统 MVP 技术方案

## 1. PRD 理解摘要

产品本质是一个**替袜子分销商做运营决策的执行系统**，不是内容生成工具。目标用户是零经验分销商（宝妈、副业人群），核心动作是"选一个目标 → 拿到一条可执行任务 → 照做发布 → 回填数据 → 拿到优化后的下一条"。MVP 要验证的核心假设是：**把运营决策压缩成一个按钮后，用户执行率能否 ≥60%，内容转化率能否 ≥15%**。PRD 提到的平台 API 自动抓取、AI 学习进化引擎、4 个意图全开、转化路径引擎、多品类支持——这些都不应进入 MVP。

***

## 2. 第一性原理拆解

### 2.1 用户目标

用户不是想"生成内容"，而是想**卖出袜子赚到钱**。内容只是手段，系统要帮用户把"不知道发什么"变成"照做就行"。

### 2.2 核心业务闭环

选择意图 → 获取唯一任务 → 用户发布 → 手动回传数据 → 规则诊断 → 生成下一条优化任务

### 2.3 核心业务对象

| 对象   | 说明                 |
| ---- | ------------------ |
| 用户   | 使用系统的人，MVP 阶段可匿名体验 |
| 意图   | 赚钱目标，MVP 仅"引流拿客户"  |
| 平台   | 抖音 / 小红书           |
| 内容任务 | 系统生成的今日唯一可执行任务     |
| 内容结构 | 钩子 + 情绪 + 转化的组合模板  |
| 发布记录 | 用户确认已发布的记录         |
| 数据回传 | 用户手动填写的播放量、评论数、私信数 |
| 诊断结果 | 基于规则判断的问题与优化方向     |
| 优化任务 | 基于诊断生成的下一条任务       |

### 2.4 核心状态变化

```
任务生成 → 待发布 → 已发布(待回填) → 已回填(待诊断) → 已诊断(待生成下一条) → 下一条任务生成
```

状态机：

* `PENDING`：任务已生成，等待用户发布

* `PUBLISHED`：用户点击"我已发布"，等待数据回填

* `REPORTED`：用户已回填数据，等待诊断

* `DIAGNOSED`：诊断完成，可生成下一条任务

* `EXPIRED`：任务过期（24h 未回填）

### 2.5 核心数据流

```
内容结构库(静态) + 意图 + 平台
    → 任务生成模块(AI 填充文案)
    → 内容任务(钩子/分镜/口播/标题/评论话术)
    → 用户发布
    → 用户手动输入(播放量/评论数/私信数)
    → 规则诊断模块
    → 诊断结果 + 优化约束
    → 任务生成模块(带优化约束)
    → 下一条优化任务
```

### 2.6 系统边界

| 边界问题           | MVP 决策            |
| -------------- | ----------------- |
| 是否自动发布内容       | **否**，用户自行发布      |
| 是否自动剪辑视频       | **否**，不在 MVP 范围   |
| 是否必须接入平台 API   | **否**，MVP 用手动输入替代 |
| 是否必须使用 AI 学习引擎 | **否**，MVP 用规则诊断替代 |
| 是否支持多品类        | **否**，仅袜子         |
| 是否支持多账号/多团队    | **否**             |
| 是否支持 4 个意图     | **否**，仅"引流拿客户"    |

## 3. MVP 范围判断

### 3.1 MVP 必须做

* 意图选择首屏（仅"引流拿客户"可用，其余灰显）

* 唯一任务界面（钩子 + 分镜 + 口播 + 标题 + 评论话术）

* "我已发布"确认流程

* 手动数据回传（播放量、评论数、私信数）

* 规则诊断（基于阈值判断问题）

* 下一条优化任务生成（带诊断约束）

* "换一条"功能（每天限 1 次）

* 图文版替代方案

### 3.2 MVP 可以简化

| PRD 需求     | MVP 简化方式               |
| ---------- | ---------------------- |
| 平台数据自动抓取   | 手动输入播放量/评论数/私信数        |
| AI 学习进化引擎  | 基于阈值的规则诊断              |
| 4 个意图全开    | 仅开放"引流拿客户"，其余灰显        |
| 实时爆款数据引擎   | 人工整理的静态结构库，运营后台手动更新    |
| 转化路径引擎     | 不做，MVP 只关注引流           |
| 24h 自动数据抓取 | 用户手动回填，24h 未填则提示       |
| 完播率数据      | MVP 不要求，仅收集播放量/评论数/私信数 |

### 3.3 MVP 不应该做

| 能力          | 不做原因                        |
| ----------- | --------------------------- |
| 平台 API 自动抓取 | 审核周期不确定，合规风险高，MVP 不应依赖外部审批  |
| AI 自主学习进化   | 数据量不足以训练，规则已够用，过早引入增加复杂度和成本 |
| 自动发布内容      | 违反平台规则，账号封禁风险，用户信任问题        |
| 自动剪辑/视频生成   | 技术复杂度高，MVP 阶段 ROI 极低        |
| 多品类支持       | 需要独立结构库和诊断规则，当前无运营资源        |
| 多账号/团队管理    | 增加权限系统复杂度，MVP 用户量不支持此需求     |
| 视频号平台       | 额外适配成本，优先抖音和小红书             |
| 投放/付费推广     | 完全不同的业务逻辑，不在核心闭环内           |

## 4. 需求到技术映射

| PRD 需求     | MVP 实现方式               | 涉及模块   | 数据依赖                                       | 验收标准                    |
| ---------- | ---------------------- | ------ | ------------------------------------------ | ----------------------- |
| 首屏 4 个意图按钮 | 渲染 4 个按钮，仅"引流"可点击，其余灰显 | 意图选择模块 | intents 表                                  | 首屏只有 4 按钮，灰显按钮点击无响应     |

| 任务界面"我已发布" | 更新任务状态为 PUBLISHED      | 发布确认模块 | content\_tasks                             | 点击后状态变更，显示追踪提示          |
| 手动数据回传     | 表单输入播放量/评论数/私信数        | 数据回传模块 | content\_tasks                             | 提交后触发诊断                 |
| 规则诊断       | 基于阈值规则判断问题类型           | 规则诊断模块 | performance\_reports + optimization\_rules | 输出诊断结果和优化方向             |
| 下一条优化任务    | 带诊断约束重新调用 AI 生成        | 任务生成模块 | diagnosis\_results                         | 新任务标注"已优化"，可追溯改了什么      |
| "换一条"      | 重新生成，每天限 1 次           | 任务生成模块 | content\_tasks                             | 第二次点击提示"今日换条次数已用"       |
| 图文版替代      | 提供图片+文案的任务格式           | 任务生成模块 | content\_structures                        | 任务界面可切换视频/图文模式          |

## 5. 总体架构设计

```
┌─────────────────────────────────────────────┐
│              客户端 (H5 SPA)                 │
│         微信内嵌 / 浏览器直接访问              │
└──────────────────┬──────────────────────────┘
                   │ HTTPS
┌──────────────────▼──────────────────────────┐
│            后端 (单体 FastAPI)                │
│  ┌──────────┬──────────┬──────────────────┐  │
│  │ 意图选择  │ 任务生成  │ 发布确认/数据回传  │  │
│  ├──────────┼──────────┼──────────────────┤  │
│  │ 规则诊断  │ 用户会话  │ 后台配置          │  │
│  └──────────┴──────────┴──────────────────┘  │
│                                              │
│  ┌─────────────────────────────────────────┐ │
│  │         内容结构库 (JSON 静态文件)        │ │
│  └─────────────────────────────────────────┘ │
│                                              │
│  ┌─────────────────────────────────────────┐ │
│  │         AI 内容生成 (Claude API)         │ │
│  └─────────────────────────────────────────┘ │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│          PostgreSQL (单库)                    │
└─────────────────────────────────────────────┘
```

### 客户端形态

H5 单页应用（Vue 3 + Vant UI），支持微信内嵌和浏览器直接访问。选择 H5 而非原生 App 的原因：MVP 阶段需要快速验证，H5 开发成本最低，且分销商主要在微信生态内活动。

### 前端

* 框架：Vue 3 + TypeScript

* UI 组件库：Vant 4（移动端优先）

* 状态管理：Pinia

* 路由：Vue Router

* 构建工具：Vite

### 后端

* 框架：FastAPI (Python 3.11+)

* 包管理：uv

* 认证：JWT（简化版，支持匿名体验）

* API 风格：RESTful

### 数据库

PostgreSQL 15+，单库单 Schema。MVP 阶段数据量小，无需分库分表。

### 内容结构库

JSON 静态文件存储，运营通过后台管理界面增删改。不使用独立数据库，直接在 PostgreSQL 中存储结构模板记录。

### AI 内容生成

deepseek v4 flash，仅用于基于结构模板填充文案。不用于诊断、不用于学习进化。

### 第三方平台接口

MVP 不接入任何平台 API。所有数据通过用户手动输入。

### 为什么这个架构足够？

MVP 核心闭环是"选意图 → 拿任务 → 发布 → 回填 → 诊断 → 下一条"。这个闭环涉及的数据操作都是简单的 CRUD + 一次 AI 调用，单体应用完全胜任。用户量在 MVP 阶段不会超过千级，单机部署足够。

### 为什么不采用更复杂方案？

| 复杂方案       | 不采用原因                             |
| ---------- | --------------------------------- |
| 微服务        | MVP 只有 1 个核心闭环，拆分增加运维成本和开发复杂度，无收益 |
| 多 Agent 系统 | 当前 AI 只做文案填充，不需要多 Agent 编排        |
| 消息队列       | 无异步任务需要解耦，AI 调用是同步的，数据回传是即时的      |
| 自动爬虫系统     | MVP 不依赖实时爆款数据，用静态结构库              |
| 自动剪辑系统     | PRD 明确排除，技术复杂度远超 MVP 范围           |
| 复杂推荐系统     | MVP 只有 1 个意图，结构库数量有限，随机 + 规则匹配即可  |
| 大规模数据中台    | MVP 数据量极小，PostgreSQL 单库足够         |

## 6. 核心模块设计

### 6.1 意图选择模块

* **模块目标**：提供用户进入系统的唯一入口

* **负责什么**：渲染意图列表，处理意图选择，引导进入任务生成

* **不负责什么**：不负责任务内容生成，不负责用户认证

* **输入**：用户点击事件

* **输出**：选中的意图 ID，跳转到任务界面

* **核心逻辑**：从 intents 表读取可用意图，标记可用/灰显状态，记录用户选择

* **依赖数据**：intents 表

* **失败情况**：intents 表为空 → 显示"系统维护中"提示

* **验收标准**：首屏只展示 4 个按钮，"引流拿客户"可点击，其余灰显，点击后 2s 内跳转

### 6.2 任务生成模块

* **模块目标**：基于意图和结构模板生成唯一可执行任务

* **负责什么**：匹配结构模板，调用 AI 填充文案，组装完整任务，处理"换一条"

* **不负责什么**：不负责诊断，不负责数据回传

* **输入**：意图 ID、平台、用户历史诊断结果（如有）、任务模式（视频/图文）

* **输出**：完整内容任务（钩子 + 分镜 + 口播 + 标题 + 评论话术 + 为什么能赚钱的说明）

* **核心逻辑**：

  1. 根据意图 + 平台从 content\_structures 匹配可用结构
  2. 如有上条诊断结果，将优化约束加入 Prompt
  3. 调用 deepseekAPI 填充文案
  4. 校验 AI 输出完整性
  5. 存储任务记录

* **依赖数据**：content\_structures、diagnosis\_results、Claude API

* **失败情况**：

  * 结构库无匹配 → 返回错误提示

  * AI 超时 → 使用模板兜底（预写好的固定文案模板）

  * AI 输出不完整 → 重试一次，仍失败则模板兜底

  * 用户已换过一条 → 提示"今日换条次数已用"

* **验收标准**：3s 内返回完整任务，包含所有必需字段，"换一条"每天限 1 次

### 6.3 内容结构库模块

* **模块目标**：维护高转化内容结构模板

* **负责什么**：存储和提供内容结构模板（钩子类型 + 情绪结构 + 转化结构）

* **不负责什么**：不负责自动爬取爆款，不负责自动更新

* **输入**：意图 ID、平台

* **输出**：匹配的结构模板列表

* **核心逻辑**：按意图 + 平台筛选，按优先级排序，随机选取一个（避免所有用户拿到相同任务）

* **依赖数据**：content\_structures 表

* **失败情况**：无匹配结构 → 返回空，触发任务生成失败

* **验收标准**：能按意图 + 平台返回至少 1 个结构模板

### 6.4 发布确认模块

* **模块目标**：记录用户发布行为，触发追踪状态

* **负责什么**：更新任务状态为 PUBLISHED，显示追踪提示

* **不负责什么**：不负责验证用户是否真的发布，不负责抓取数据

* **输入**：任务 ID

* **输出**：确认成功，显示"正在追踪你的内容表现"

* **核心逻辑**：校验任务属于当前用户且状态为 PENDING，更新状态，设置 24h 提醒定时器

* **依赖数据**：content\_tasks 表

* **失败情况**：任务不存在 / 状态不对 → 返回错误提示

* **验收标准**：点击后状态变为 PUBLISHED，显示追踪提示

### 6.5 数据回传模块

* **模块目标**：收集用户手动输入的内容表现数据

* **负责什么**：提供回填表单，校验输入合理性，存储数据，触发诊断

* **不负责什么**：不负责自动抓取数据

* **输入**：任务 ID、播放量、评论数、私信数

* **输出**：回填成功，触发规则诊断

* **核心逻辑**：

  1. 校验任务状态为 PUBLISHED
  2. 校验输入值合理性（播放量 ≥ 0，不超过 1 亿等）
  3. 存储到 performance\_reports
  4. 调用规则诊断模块

* **依赖数据**：content\_tasks、performance\_reports

* **失败情况**：输入值异常 → 提示具体错误（如"播放量不能为负数"）

* **验收标准**：提交后数据存储成功，诊断结果可查看

### 6.6 规则诊断模块

* **模块目标**：基于回传数据判断内容问题并给出优化方向

* **负责什么**：应用诊断规则，输出问题类型和优化方向

* **不负责什么**：不负责 AI 学习，不负责自动调整规则

* **输入**：performance\_reports 记录

* **输出**：诊断结果（问题类型 + 优化方向 + 具体建议）

* **核心逻辑**：按规则表逐条匹配，取优先级最高的问题

* **依赖数据**：performance\_reports、optimization\_rules

* **失败情况**：无匹配规则 → 返回"数据表现正常，继续保持"

* **验收标准**：输入数据后 1s 内返回诊断结果

### 6.7 下一条任务优化模块

* **模块目标**：基于诊断结果生成优化后的下一条任务

* **负责什么**：将诊断约束注入任务生成 Prompt，标注优化说明

* **不负责什么**：不负责自动推送（MVP 用户手动触发）

* **输入**：诊断结果 ID

* **输出**：优化后的内容任务

* **核心逻辑**：

  1. 读取诊断结果
  2. 构造优化约束 Prompt 片段
  3. 调用任务生成模块（带约束）
  4. 在任务中标注"已针对上次问题优化"和具体改动说明

* **依赖数据**：diagnosis\_results、content\_structures、Claude API

* **失败情况**：诊断结果不存在 → 按普通任务生成

* **验收标准**：新任务标注优化说明，用户可看到"改了什么、为什么改"

### 6.8 用户与会话模块

* **模块目标**：管理用户身份和会话

* **负责什么**：匿名访问时生成本地标识，登录时关联账号，管理会话状态

* **不负责什么**：不负责平台账号授权（MVP 不做）

* **输入**：首次访问 / 登录请求

* **输出**：用户 ID + JWT Token

* **核心逻辑**：

  1. 首次访问：生成匿名用户记录，返回 JWT
  2. 登录：手机号 + 验证码，关联匿名用户历史数据
  3. 会话管理：JWT 有效期 7 天

* **依赖数据**：users 表

* **失败情况**：验证码错误 → 提示重试

* **验收标准**：匿名用户可完成完整闭环，登录后数据不丢失

### 6.9 后台配置模块

* **模块目标**：提供运营人员管理内容结构库和诊断规则的能力

* **负责什么**：内容结构 CRUD、诊断规则 CRUD、查看用户数据统计

* **不负责什么**：不负责自动运营

* **输入**：运营人员的配置操作

* **输出**：配置变更结果

* **核心逻辑**：标准 CRUD + 简单统计面板

* **依赖数据**：content\_structures、optimization\_rules、content\_tasks、performance\_reports

* **失败情况**：配置冲突 → 提示具体问题

* **验收标准**：运营可增删改结构模板和诊断规则，可查看用户任务和回填数据

## 7. 核心业务流程

### 7.1 用户首次使用流程

```
用户打开 H5 → 系统生成匿名用户 → 首屏展示 4 个意图按钮
→ 用户点击"引流拿客户" → 系统匹配结构模板 + 调用 AI 生成任务
→ 展示任务界面（钩子/分镜/口播/标题/话术/为什么能赚钱）
```

### 7.2 用户发布确认流程

```
用户在任务界面点击"我已发布" → 系统更新任务状态为 PUBLISHED
→ 显示"正在追踪你的内容表现" → 提示用户 24h 内回填数据
```

### 7.3 数据回传流程

```
用户进入"我的任务" → 选择已发布任务 → 填写播放量/评论数/私信数
→ 提交 → 系统校验输入 → 存储到 performance_reports
→ 触发规则诊断 → 生成诊断结果 → 提示用户查看诊断和下一条任务
```

### 7.4 诊断与下一条任务流程

```
用户查看诊断结果 → 系统展示问题诊断（如"钩子弱，完播率低"）
→ 用户点击"获取下一条任务" → 系统将诊断约束注入 Prompt
→ 调用 AI 生成优化任务 → 展示新任务，标注"已针对上次问题优化"
→ 展示优化说明（改了什么、为什么改）
```

### 7.5 异常流程

#### 用户当天已有未完成任务

```
用户进入系统 → 检测到 PENDING/PUBLISHED 状态的任务
→ 弹窗提示"你还有一个任务未完成，继续还是重新选择？"
→ 继续：跳转到该任务界面
→ 重新选择：将旧任务标记 EXPIRED，生成新任务
```

#### 用户觉得内容不合适

```
用户点击"换一条" → 检查今日换条次数
→ 未用过：重新生成任务，计数 +1
→ 已用过：提示"今日换条次数已用，明天再来"
```

#### 用户没有拍摄条件

```
用户点击"切换图文模式" → 系统基于图文结构模板重新生成任务
→ 任务内容为图片描述 + 文案（无需拍摄）
```

#### 用户 24h 内没有回填数据

```
系统检测 PUBLISHED 状态超过 24h 的任务
→ 推送提醒"请回填你的内容数据"
→ 超过 48h 仍未回填 → 任务标记 EXPIRED，允许生成新任务
```

#### AI 生成失败

```
AI 调用超时（>10s）→ 重试一次
→ 仍失败 → 使用预置模板兜底（从 content_structures 中取固定文案）
→ 提示用户"当前使用模板内容，可换一条获取定制内容"
```

#### 内容结构库为空或匹配失败

```
按意图+平台查询无结果 → 返回错误"暂无可用内容结构"
→ 后台告警通知运营补充结构
→ 用户看到"系统维护中，请稍后再试"
```

## 9. API 设计

### 9.1 获取意图列表

* **Method**: GET

* **Path**: `/api/v1/intents`

* **认证**: 不需要

* **请求参数**: 无

* **返回结果**:

```json
{
  "intents": [
    {
      "id": "uuid",
      "name": "引流拿客户",
      "description": "我想让更多人看到我",
      "is_active": true,
      "sort_order": 1
    }
  ]
}
```

* **核心校验逻辑**: 无

* **错误情况**: 无

### 9.2 选择意图并生成任务

* **Method**: POST

* **Path**: `/api/v1/tasks`

* **认证**: 需要（JWT，匿名用户也有 token）

* **请求参数**:

```json
{
  "intent_id": "uuid",
  "platform_id": "uuid",
  "task_type": "video"
}
```

* **返回结果**:

```json
{
  "task": {
    "id": "uuid",
    "platform_name": "抖音",
    "hook_text": "3秒钩子文案",
    "storyboard": [
      {"shot": 1, "description": "镜头描述", "duration": "3s"}
    ],
    "script_text": "完整口播文案",
    "title": "发布标题 #话题",
    "comment_template": "评论区置顶话术",
    "why_it_works": "为什么这条内容能赚钱",
    "is_optimized": false,
    "created_at": "2026-05-20T10:00:00Z"
  }
}
```

* **核心校验逻辑**:

  * intent\_id 对应的意图 is\_active 必须为 true

  * 用户当天不能有 PENDING 状态的任务（如有则返回该任务）

  * 用户当天 PUBLISHED 状态任务不超过 3 个

* **错误情况**:

  * 意图不可用 → 400 "该意图暂未开放"

  * 有未完成任务 → 409 返回已有任务

  * AI 生成失败 → 返回模板兜底内容

### 9.3 获取当前任务

* **Method**: GET

* **Path**: `/api/v1/tasks/current`

* **认证**: 需要

* **请求参数**: 无

* **返回结果**: 同 9.2 的 task 结构

* **核心校验逻辑**: 查询用户最新的非 EXPIRED 任务

* **错误情况**: 无任务 → 404

### 9.4 换一条任务

* **Method**: POST

* **Path**: `/api/v1/tasks/{task_id}/swap`

* **认证**: 需要

* **请求参数**: 无

* **返回结果**: 新任务结构（同 9.2）

* **核心校验逻辑**:

  * 任务属于当前用户

  * 用户今日 swap\_count < 1

* **错误情况**:

  * 今日已换过 → 429 "今日换条次数已用"

  * 任务不属于当前用户 → 403

### 9.5 确认已发布

* **Method**: POST

* **Path**: `/api/v1/tasks/{task_id}/publish`

* **认证**: 需要

* **请求参数**: 无

* **返回结果**:

```json
{
  "message": "正在追踪你的内容表现",
  "task_id": "uuid",
  "status": "PUBLISHED"
}
```

* **核心校验逻辑**:

  * 任务状态为 PENDING

  * 任务属于当前用户

* **错误情况**:

  * 状态不对 → 400 "任务状态不正确"

  * 任务不属于当前用户 → 403

### 9.6 提交数据回传

* **Method**: POST

* **Path**: `/api/v1/tasks/{task_id}/report`

* **认证**: 需要

* **请求参数**:

```json
{
  "play_count": 1200,
  "comment_count": 5,
  "message_count": 2
}
```

* **返回结果**:

```json
{
  "diagnosis": {
    "problem_type": "hook_weak",
    "problem_desc": "播放量偏低，钩子吸引力不足",
    "optimization_direction": "强化前3秒钩子",
    "optimization_detail": "建议使用反常识或痛点型钩子..."
  }
}
```

* **核心校验逻辑**:

  * 任务状态为 PUBLISHED

  * play\_count ≥ 0, comment\_count ≥ 0, message\_count ≥ 0

  * play\_count ≤ 100000000

  * 该任务未回填过

* **错误情况**:

  * 数值异常 → 400 具体字段错误

  * 已回填过 → 409 "该任务已回填数据"

### 9.7 获取诊断结果

* **Method**: GET

* **Path**: `/api/v1/tasks/{task_id}/diagnosis`

* **认证**: 需要

* **请求参数**: 无

* **返回结果**: 同 9.6 的 diagnosis 结构

* **核心校验逻辑**: 任务状态为 DIAGNOSED

* **错误情况**: 未诊断 → 404

### 9.8 获取下一条优化任务

## 10. AI 能力设计

### 10.1 AI 在 MVP 中负责什么

* 基于结构模板生成口播文案

* 生成 3 秒钩子文案

* 生成分镜脚本描述

* 生成发布标题（含话题标签）

* 生成评论区置顶话术

* 生成"为什么这条内容能赚钱"说明

* 在优化任务中，基于诊断约束调整上述内容

### 10.2 AI 在 MVP 中不负责什么

* 不负责自动判断真实成交

* 不负责自动爬取平台爆款

* 不负责自主学习进化

* 不负责自动发布内容

* 不负责诊断（由规则模块负责）

* 不负责选择内容结构（由匹配逻辑负责）

### 10.3 Prompt 输入结构

```
你是一名袜子分销内容策划专家。

## 任务
基于以下内容结构模板，生成一条完整的短视频内容任务。

## 用户意图
{intent_name}：{intent_description}

## 发布平台
{platform_name}

## 产品类型
袜子（分销模式）

## 目标人群
对袜子有需求的普通消费者，尤其是注重性价比和实用性的群体

## 内容结构模板
- 钩子类型：{hook_type}
- 情绪结构：{emotion_structure}
- 转化结构：{conversion_structure}

## 优化约束（如有上条诊断）
{optimization_prompt}

## 禁用表达
- 不得出现"最便宜""全网最低"等绝对化用语
- 不得出现医疗功效承诺
- 不得出现虚假收益承诺
- 不得出现"月入过万"等夸大宣传

## 输出格式（严格 JSON）
{
  "hook_text": "3秒钩子文案，15字以内",
  "storyboard": [
    {"shot": 1, "description": "镜头描述", "duration": "3s"},
    {"shot": 2, "description": "镜头描述", "duration": "5s"},
    {"shot": 3, "description": "镜头描述", "duration": "10s"}
  ],
  "script_text": "完整口播文案，100-200字",
  "title": "发布标题，含2-3个话题标签",
  "comment_template": "评论区置顶话术，引导私信或互动",
  "why_it_works": "一句话说明为什么这条内容能赚钱"
}
```

### 10.4 AI 输出校验

| 校验项               | 规则          | 失败处理  |
| ----------------- | ----------- | ----- |
| JSON 格式           | 必须是合法 JSON  | 重试一次  |
| hook\_text        | 非空，≤30 字    | 截断或重试 |
| storyboard        | 3-5 个镜头     | 重试    |
| script\_text      | 非空，50-300 字 | 截断或重试 |
| title             | 非空，≤50 字    | 截断    |
| comment\_template | 非空          | 重试    |
| why\_it\_works    | 非空          | 重试    |
| 违规表达              | 不含禁用词列表中的词  | 重试    |
| 场景偏离              | 包含"袜子"相关关键词 | 重试    |
| 虚假承诺              | 不含收益承诺      | 重试    |

### 10.5 AI 失败兜底

| 失败情况         | 处理方式                             |
| ------------ | -------------------------------- |
| API 超时（>10s） | 重试 1 次，仍超时则使用 fallback\_content  |
| 输出不完整        | 重试 1 次，仍不完整则使用 fallback\_content |
| 内容质量差（校验不通过） | 重试 1 次，仍不通过则使用 fallback\_content |
| API 限流       | 使用 fallback\_content，记录日志        |
| API 不可用      | 使用 fallback\_content，告警通知        |

fallback\_content 来自 content\_structures 表的 fallback\_content 字段，由运营预先填写。

### 10.6 成本控制

| 措施     | 说明                                                  |
| ------ | --------------------------------------------------- |
| 模板复用   | 相同意图+平台+钩子类型的任务，24h 内缓存 AI 输出，不同用户可复用               |
| 生成频率限制 | 每用户每天最多生成 2 条任务（1 条初始 + 1 条换条）                      |
| 换条限制   | 每天限 1 次                                             |
| 模型选择   | 使用 claude-sonnet-4-20250514，平衡质量和成本                 |
| 日志     | 记录每次 AI 调用的 input token / output token / 耗时 / 是否成功  |
| 缓存策略   | 按 intent\_id + platform\_id + hook\_type 缓存，TTL 24h |

## 11. 规则诊断与优化逻辑

### 11.1 输入指标

| 指标             | 来源     | 范围              |
| -------------- | ------ | --------------- |
| play\_count    | 用户手动输入 | 0 - 100,000,000 |
| comment\_count | 用户手动输入 | 0 - 1,000,000   |
| message\_count | 用户手动输入 | 0 - 100,000     |

### 11.2 诊断规则

| 数据表现                                                        | 可能问题      | problem\_type     | 优化方向               |
| ----------------------------------------------------------- | --------- | ----------------- | ------------------ |
| play\_count < 500                                           | 标题/封面/选题弱 | title\_weak       | 换钩子类型，优化标题写法       |
| play\_count ≥ 500 且 comment\_count < 5                      | 互动引导弱     | interaction\_weak | 强化评论区话术，增加互动钩子     |
| comment\_count ≥ 5 且 message\_count = 0                     | 转化话术弱     | conversion\_weak  | 优化评论区引导私信的话术       |
| play\_count ≥ 500 且 comment\_count ≥ 5 且 message\_count ≥ 1 | 表现正常      | normal            | 继续当前策略，微调优化        |
| play\_count < 200                                           | 钩子极弱      | hook\_weak        | 必须更换钩子类型，使用反常识或痛点型 |

### 11.3 下一条任务生成策略

| problem\_type     | 结构调整                | Prompt 注入                                        |
| ----------------- | ------------------- | ------------------------------------------------ |
| hook\_weak        | 强制切换钩子类型（如场景切入→反常识） | "上条内容钩子吸引力极弱，请使用{新钩子类型}，前3秒必须制造强烈反差或悬念"          |
| title\_weak       | 保留钩子类型，优化标题策略       | "上条内容标题曝光不足，请使用数字+痛点组合标题，加入2个热门话题标签"             |
| interaction\_weak | 保留结构，增加互动设计         | "上条内容互动率低，请在口播结尾增加提问式互动引导，评论区话术增加话题讨论"           |
| conversion\_weak  | 保留结构，强化转化话术         | "上条内容私信转化低，请在评论区话术中增加具体利益点（如'私信我领XX'），口播中增加行动指令" |
| normal            | 保留当前结构，微调细节         | "上条内容表现良好，请在此基础上微调，尝试不同的情绪结构变体"                  |

## 12. 权限、安全与合规

### 匿名体验处理

* 首次访问自动生成匿名用户，JWT 有效期 7 天

* 匿名用户可完成完整闭环（选意图→拿任务→发布→回填→诊断→下一条）

* 匿名用户限制：每天最多生成 2 条任务

### 注册/登录时机

* 用户可随时选择登录（手机号+验证码）

* 登录后关联匿名用户的历史数据

* 不强制登录，但建议登录以防数据丢失

### 用户平台授权

* MVP 不要求用户授权平台账号

* MVP 不读取用户平台账号数据

* 所有数据通过用户手动输入

### 数据存储安全

* 用户内容数据存储在 PostgreSQL，应用层加密敏感字段

* JWT token 哈希存储，不存明文

* 手机号加密存储

### 手动输入防误填

* 前端：数值类型校验，范围校验（播放量 0-1 亿）

* 后端：重复校验逻辑，异常值告警（如播放量 > 1000 万标记为需人工复核）

* 不阻止用户提交，但对异常值标记

### AI 生成内容合规

* Prompt 中明确禁用违规表达

* 输出校验包含违规词检测

* 运营可配置禁用词列表

* 不保证 100% 合规，运营需定期抽检

### 平台规则遵守

* 系统不代替用户自动发布内容（避免账号封禁风险）

* 系统不爬取平台数据（MVP 阶段）

* 生成内容仅供参考，用户自行判断是否发布

### 为什么系统不应代替用户自动发布

1. 违反平台规则，可能导致账号封禁
2. 用户无法掌控发布内容，信任度低
3. 不同用户账号权重不同，自动发布效果不可控
4. 法律风险：自动发布可能被视为虚假宣传

## 13. 非功能性要求

### 响应时间

* 意图列表加载：≤500ms

* 任务生成（含 AI 调用）：≤5s（目标 3s，AI 调用是瓶颈）

* 数据回传提交：≤500ms

* 诊断结果返回：≤200ms（纯规则计算）

**实现方式**：

* AI 调用设置 10s 超时，超时走兜底

* 数据库查询添加必要索引

* 前端使用骨架屏优化感知速度

### 可用性

* 目标 ≥99%（核心任务生成链路）

* **实现方式**：单机部署 + 进程守护（Docker restart policy: always）+ 健康检查端点

### 数据一致性

* 任务状态变更使用数据库事务保证一致性

* AI 生成失败不写入任务记录

* **实现方式**：FastAPI 依赖注入数据库 session，事务自动提交/回滚

### 日志

* 结构化 JSON 日志

* 记录：请求路径、响应状态、耗时、用户 ID

* AI 调用单独记录：input/output token、耗时、是否成功、是否兜底

* **实现方式**：Python logging + structlog

### 监控

* MVP 阶段：简单健康检查端点 `/health`

* 关键指标：任务生成成功率、AI 调用成功率、AI 平均耗时

* **实现方式**：FastAPI 中间件记录指标，运营后台展示基础统计

### 数据备份

* PostgreSQL 每日自动备份

* 保留 7 天备份

* **实现方式**：pg\_dump cron job + 对象存储上传

### 成本控制

* 服务器：2C4G 云服务器，月费约 ¥200

* AI 调用：预估每用户每天 2 次调用，100 用户/天 ≈ 200 次调用，月费约 ¥300-500

* 数据库：使用同一台服务器自建 PostgreSQL，无额外费用

* **总月费预估**：¥500-700

### 后台可配置能力

* 内容结构模板 CRUD

* 诊断规则 CRUD

* 禁用词列表配置

* AI Prompt 模板配置

* 意图开关（is\_active）

* 平台开关

## 17. 最终技术建议

### 推荐的 MVP 技术路线

H5 单页应用（Vue 3 + Vant）+ 单体后端（FastAPI + PostgreSQL）+ Claude API 文案生成 + 规则诊断。Docker Compose 单机部署。不引入微服务、消息队列、自动爬虫、自动剪辑。

### 当前最应该优先开发的闭环

**"选意图 → 拿任务 → 发布 → 回填 → 诊断 → 下一条"**。这是验证核心假设的唯一路径。第一周就应该跑通骨架流程（即使用固定模板），而不是花时间在 AI 调优或结构库建设上。

### 当前最不应该过早投入的方向

1. **平台 API 接入**：审核周期不确定，MVP 不应被外部依赖阻塞
2. **AI 学习进化引擎**：数据量不足，规则已够用
3. **多意图开发**：先验证一个意图的闭环是否成立
4. **自动发布/自动剪辑**：技术复杂度和合规风险远超 MVP 范围

### 产品方必须优先确认的问题

1. **内容结构库的初始数据由谁提供？** 需要运营团队在开发第 2 周前提供至少 20 个验证过的结构模板
2. **AI 生成内容的合规责任归属？** 需要明确用户发布 AI 生成内容后的责任边界
3. **MVP 是否需要用户协议/隐私政策？** 收集手机号和数据回传需要法律合规
4. **抖音/小红书平台账号是否需要提前申请？** 即使 MVP 不用 API，Phase 2 需要，建议提前启动

### 技术团队第一周应该做什么

1. 初始化项目结构（前端 Vue 3 + 后端 FastAPI + Docker Compose）
2. 搭建数据库 schema 和基础 API
3. 实现匿名用户注册 + JWT
4. 用固定模板跑通"选意图→看任务→点发布"的前后端流程
5. 确认 Claude API 可用性和调用方式
